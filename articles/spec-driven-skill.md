## はじめに

半年ほど前から、自分用のプランモード＆実装モード用のスキルを作って運用していますが、個人的にかなり良い感じで実装ができています。

元々作成しようと思ったきっかけは、Kiro の Spec モードを使用した際に、実装計画とタスクの md ファイルを作成することを面白いと感じ、Claude Code でもこれに似たファイルを作成して実装を進めたいと考えたからです。

## プランモードの限界

Claude Code の標準のプランモードは、基本的に Ask ツールでのやり取りの結果が md ファイル1つに書き出されます。ただ、運用していく中で以下のような不便さを感じるようになりました。

- 探索結果やユーザーへの質問内容などを、独立したファイルとして残せない
- 出力先が md に固定されるため、技術的な解説を HTML で作らせるといった応用がしづらい

そこで、実装計画・タスクに加えてテストケースや技術解説なども生成でき、かつ自分なりのフォーマットを強制できるスキルを作ることにしました。目的は以下の3つです。

- 実装時の認知負荷を下げる
- テストケースの抜け漏れを減らす
- 実装計画を徹底的に詰める

## 作ったスキルの全体像

大きくは、以下の2つのスキルを組み合わせて使っています。

- **プランモードスキル**: 探索・要件整理・実装計画とタスクへの落とし込みまでを行う
- **実装モードスキル**: プランモードで作成した成果物をもとに実装を進める

プランモードで作成したファイルは、計画ごとにフォルダにまとめ、フォルダ名にインデックス（連番）を付与します。実装モードはこのインデックスを引数で受け取り、省略時は最新のものを対象とします。

出力されるフォルダ構成のイメージは以下です。

```
.plugin-workspace/.specs/001-feature-name/
├── PLANNING            # フェーズマーカー（存在する間は計画中）
├── requirements.md     # 要件
├── design.md           # 設計
├── tasks.md            # タスク一覧（□ / ■ で進捗管理）
└── notes/              # 探索結果や調査メモ
```

## 工夫

このスキルには、自分なりにいくつか工夫を加えている点があります。

### 1. 出力を分割する設計

標準のプランモードのように1枚の md にすべてを詰め込むのではなく、フェーズや用途ごとにファイルを分けて出力する構成にしました。要件・設計・タスク・調査メモをそれぞれ別ファイルに切り出しておく、というシンプルな方針です。

分割しておくと、次のような利点があります。

- 成果物ごとに出力形式を変えられる（テストケースは HTML、実装計画は md、といった使い分けができる）
- 特定の目的に沿ったファイルだけを開いて確認できる
- 特定のフェーズだけをあとから差し替えられる
- `PLANNING` ファイルの有無をフェーズマーカーとして使えるので、後述するガード処理や自動アーカイブと連動させやすい

要は、md 1枚に詰め込んだ状態だと難しかった「フェーズ単位での取り回し」を、ファイル分割によって成立させている、というのがポイントです。

### 2. 出力形式を設定ファイルで切り替える

用途によっては、md ではなく HTML で技術解説を出したいケースがあります。そこでスキル側にはハードコードせず、設定ファイルで出力形式を切り替えられるようにしました。

`.plugin-workspace/.specs/.config.yml` のようなファイルに、成果物ごとの出力形式を書いておくイメージです。

```yaml
output-formats:
  implementation-plan: md
  design-doc: md
  tech-reference: html
  test-cases: html
```

スキルの起動時にこの設定を読んで、`.md` を作るか `.html` を作るかを分岐します。プラン起動のたびにプロンプトで「これは HTML で」と指示し直さなくてよいので、繰り返し使ったときの再現性が上がりました。

設定はプロジェクトごとに持てるので、「このプロジェクトは全部 md でいい」「ここは技術解説だけ HTML にしたい」といった使い分けもできます。

### 3. Hooksによるガード

プランモード中にソースコードなどのファイルを勝手に書き換えられると困るので、Claude Code の Hooks を使ってガードをかけています。

Claude Code の Hooks では、現在のセッション ID を含む情報が JSON で渡ってくるので、これを利用して「このセッションは今、計画モード中である」という状態をファイルで表現します。

具体的には、スキル起動時にセッション ID と同名のガードファイルを生成します。

```
.plugin-workspace/.specs/.guard/{SESSION_ID}
```

このファイルが存在している間は、`PreToolUse` フックで Write / Edit / MultiEdit / Bash をブロックする、という単純な仕組みです。

#### ガードスクリプトの中身

シェルスクリプト側では、標準入力から渡ってくる JSON からセッション ID とツール名を取り出し、対応するガードファイルの有無で挙動を切り替えます。`exit 2` を返すとツール実行がブロックされ、標準エラー出力の内容がモデルへのフィードバックとして渡ります。

```bash
INPUT=$(cat)
SESSION_ID=$(echo "$INPUT" | jq -r '.session_id // empty')
TOOL=$(echo "$INPUT" | jq -r '.tool_name // empty')

GUARD_FILE=".plugin-workspace/.specs/.guard/${SESSION_ID}"

# ガードファイルが無ければ素通り
[ ! -f "$GUARD_FILE" ] && exit 0

# Write / Edit: .specs/ 以外への書き込みをブロック
if [ "$TOOL" = "Write" ] || [ "$TOOL" = "Edit" ] || [ "$TOOL" = "MultiEdit" ]; then
  FILE=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')
  echo "$FILE" | grep -qE '(^|/)\.plugin-workspace/\.specs/' && exit 0

  echo "【計画モード】${FILE} への書き込みはブロックされました。" >&2
  exit 2
fi
```

Bash ツールについても同様に、リダイレクト（`>` / `>>`）や `tee` / `sed -i` / `cp` / `mv` / `rm` / `mkdir` といった書き込み系コマンドをパターンマッチで拾ってブロックしています。`.plugin-workspace/.specs/` 配下への操作だけは例外的に許可することで、計画ファイルの生成・更新はそのまま行えるようにしています。

#### ガード解除

ガードファイルはセッション ID ごとに作られるので、`/clear` して別セッションで実装モードを起動すれば、そのセッションにはガードがかかりません。自分の場合は計画が終わったら一度 `/clear` してから実装モードに入ることが多いので、実質これが解除手順になっています。もちろん、ガードファイルを手動で削除しても解除できます。

モデル側から `rm` でガードファイルを消そうとした場合は、Bash フック側で検出してブロックしています。同じセッションのまま、勝手に実装フェーズへ移行してしまうことを防ぐためです。

### 4. Hooksでセッション名を自動リネームする

複数の spec を並行で回していると、Claude Code のセッション一覧を見たときに「どれがどの spec のどのフェーズなのか」が分からなくなりがちです。

これも Hooks で解決していて、`UserPromptSubmit` フックで、現在触っている spec 名やフェーズを組み合わせたセッションタイトルを自動で付与するようにしました。

`UserPromptSubmit` は、フックの標準出力に `hookSpecificOutput.sessionTitle` を含む JSON を返すと、Claude Code 側がその値をセッションタイトルとして使ってくれます。以下のようなフックでタイトルを組み立てています。

```bash
PROMPT=$(echo "$INPUT" | jq -r '.prompt // empty')

case "$PROMPT" in
  /spec-driven-dev*) LABEL="📋 plan" ;;
  /spec-implement*)  LABEL="🔨 impl" ;;
  *) exit 0 ;;
esac

# プロンプト or specs ディレクトリから spec 番号を拾って付与
NUM=$(grep -oE '#[0-9]+' <<<"$PROMPT" | head -1)
[ -n "$NUM" ] && LABEL="${LABEL} ${NUM}"

jq -nc --arg t "$LABEL" \
  '{hookSpecificOutput:{hookEventName:"UserPromptSubmit",sessionTitle:$t}}'
```

これで「📋 plan #003」「🔨 impl #002」のようなタイトルが自動で並びます。個人的に一番ありがたいのは、複数のセッションを同時に動かしているときに、どれが計画モードでどれが実装モードなのかが一発で分かる点です。

### 5. 要件の未確定事項が残っている間は計画進行をブロックする

要件が決まりきっていないまま計画の作成に移ってしまわないように、ここにもブロックをかけています。

具体的には、実装計画に入る前段階として `requirements.md` の中に「未解決の確認事項」チェックボックス（`□`）を持たせておき、ここが残ったまま `implementation-plan.md` を書こうとするとフック側でブロックする、という仕組みです。

チェックの流れはシンプルで、`implementation-plan` に対する Write / Edit が来たときだけ発動し、同じフォルダの `requirements.md` の該当セクションを覗きに行きます。

```bash
case "$FILE" in
  *implementation-plan*) ;;
  *) exit 0 ;;
esac

REQ_FILE="$(dirname "$FILE")/requirements.md"
section=$(sed -n '/^#\{1,4\}.*未解決の確認事項/,/^#\{1,4\} /p' "$REQ_FILE")

if echo "$section" | grep -qE '^[[:space:]]*□'; then
  echo "【requirements】未解決事項が残っています: ${REQ_FILE}" >&2
  exit 2
fi
```

### 6. Stopフックで完了specを自動アーカイブする

セッション終了時、`Stop` フックで `.plugin-workspace/.specs/` の中を走査して、PLANNING ファイルが残っていない spec フォルダを `archive/` 配下に自動で移動するようにしています。

```bash
for dir in .plugin-workspace/.specs/[0-9][0-9][0-9]-*/; do
  [ -d "$dir" ] || continue
  [ -f "${dir}PLANNING" ] && continue  # まだ計画中はスキップ

  mkdir -p .plugin-workspace/.specs/archive
  mv "$dir" .plugin-workspace/.specs/archive/
done
```

「PLANNING を消した ＝ 実装完了」という判定基準です。手動でやると絶対にサボりがちなアーカイブが、勝手に済んでいる状態を作れるので、ワークスペースが常にクリーンな状態で保たれます。

## まとめ

このスキルの本質は、自分なりの出力形式やルールを、スキルと Hooks で強制できる点です。プランモードそのものを AI に任せるのではなく、「どのファイルにどんな粒度で出力するか」「いつ実装を許可するか」といった運用ルールを、自分の手元で設計できるのが気に入っています。
